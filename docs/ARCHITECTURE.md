# Architecture

The app is two independent pieces that talk over a small REST API:

```
┌──────────────────────────────┐        HTTP /api/*        ┌──────────────────────────────┐
│  Frontend (Vite + Three.js)  │  ───────────────────────► │  Backend (FastAPI, Python)   │
│                              │  ◄─────────────────────── │                              │
│  • 3D satellite globe        │      JSON responses       │  • routers/  (HTTP layer)    │
│  • 2D map + Street View       │                           │  • services/ (API clients +  │
│  • detail / route / bucket UI │                           │     mock fallback)           │
│  • dashed route lines         │                           │  • ml/       (price models)  │
└──────────────────────────────┘                           └──────────────────────────────┘
        │                                                            │
        │ Google Maps JS (satellite + Street View, browser key)      │ Amadeus · OpenWeather · Google Places
        ▼                                                            ▼
   viewer's browser                                          third-party APIs (optional)
```

In development, Vite proxies `/api/*` to `http://localhost:8000` (see `vite.config.js`),
so the browser only ever talks to one origin and there is no CORS friction.

## Request flow: opening a destination

1. User clicks a pin (Three.js raycaster) or a nav item → `main.js#selectDestination`.
2. `detailPanel.open(dest)` renders static content immediately, then fires **three
   parallel** calls: `GET /api/flights`, `GET /api/predict/price`, `GET /api/predict/best-time`.
3. Each backend router calls a **service**. Services check `config.has_*`:
   - key present → real API (Amadeus / OpenWeather / Google).
   - key absent or request fails → deterministic **mock** (`services/mock_data.py`).
4. `flightPanel.js` renders the results (offers table, ML badge, SVG price curve,
   best-time bar chart) into the panel.

## Request flow: planning a route

1. User adds stops (from a destination or a searched place) → `routePlanner.addStop`.
2. The planner posts the ordered stops (optionally prefixed with New York) to
   `POST /api/routes/plan`. The backend computes great-circle legs + totals and, if
   `optimize` is set, reorders them with a nearest-neighbour heuristic.
3. `globe.setRoute(stops)` draws dashed great-circle `THREE.Line`s just above the
   globe surface (`globe/routes.js`).

## Request flow: adding a custom destination

1. User opens **＋ Add Destination**, types a name → `GET /api/places/geocode` (unbounded
   worldwide search: Google Text Search when keyed, else OSM/Nominatim).
2. Picking a result posts it to `POST /api/destinations`. The backend slugifies an id,
   fills in the **nearest airport** (`nearest_airport`), applies sensible defaults, and
   **persists** it to `data/custom_destinations.json`.
3. The frontend adds a nav item + globe pin and selects it. Because every service
   resolves coordinates/airport via `by_id` (which now also checks the custom registry),
   flights, weather, ML prediction and routes work for it **immediately** — no special
   casing. On the next page load, `main.js` re-fetches `GET /api/destinations` and
   restores any custom entries, so they survive reloads. Custom destinations can also be
   removed (`DELETE /api/destinations/{id}`); built-ins cannot.

## Why the mock fallback matters

Every third-party dependency is optional and isolated in one service file. That gives
you three properties: the app **always runs** (great for onboarding/CI), you can
develop **offline**, and mock prices are generated by the *same* function the ML model
trains on, so demo data and predictions never contradict each other.
